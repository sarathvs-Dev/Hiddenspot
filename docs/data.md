# Demo data system

Phase 1 runs entirely on local data. There is no backend, no database and no cloud sync.
This document explains the data model, the business rules, and how changes are stored.

## Important: what this data is and is not

- **Places are real, well-known Kerala destinations** with their correct district. Only facts
  that are widely established are included: the name, the district and the kind of place.
- **Coordinates are cross-checked, never guessed.** A coordinate is stored only when Wikipedia
  and OpenStreetMap agree: within 3 km for a specific site, or 10 km for an area such as a
  village or protected area. 30 of the 38 real places passed: 17 at site level and 13 at area
  level. Every one cites both sources and the retrieval date in `sources`. The other 8 stayed
  `null`, because the sources disagreed or only one existed. The reasons are recorded in
  `packages/shared/scripts/verified-coordinates.json`.
- **Other unknown facts are `null`.** `address`, `openingHours` and `entryFee` are null for
  every place. Hours and fees change often and could not be confirmed from a stable source.
  The apps show "Not confirmed yet".
- **Directions:** site-level places open directions to the coordinates. Area-level and unknown
  locations open a map search by name and district, because an area centre is not a destination.
- **Synthetic entries are labelled.** Three fictional places have `isSyntheticDemo: true` and
  a name ending in "(demo)". The apps show a "Demo listing" badge on them. Submission drafts
  are fictional too, and their names also end in "(demo)".
- **Reviews, ratings, popularity and users are sample data.** Demo users are fictional
  (`isDemo: true`). Review text is generic sample text, not real visitor feedback, and the apps
  label it "Sample review". `popularityCount` is a synthetic number used only for sorting.
- **Best-time and safety text is general guidance per category**, such as "rocks near water are
  slippery". It is not a verified fact about any specific place.
- **Photos are placeholders** from picsum.photos and do not show the named places.

## Files

All seed data lives in `packages/shared/data` and is never modified at runtime.

| File               | Contents                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------- |
| `places.json`      | 41 places, 38 real and 3 synthetic, covering 13 of the 14 districts and all 8 categories |
| `categories.json`  | 8 categories with icon keys and display order                                            |
| `reviews.json`     | 61 sample reviews from demo users                                                        |
| `demoUsers.json`   | 9 demo users: explorers, a moderator and the curator account                             |
| `submissions.json` | 6 demo submissions, one in every moderation status                                       |
| `kerala.ts`        | The 14 Kerala districts, used for validation and filters                                 |

The JSON is generated by `packages/shared/scripts/generate-seed.mjs`, so ids, coordinates and
rating totals stay consistent. Change the script or `verified-coordinates.json`, then run:

```bash
npm run seed:generate
npm test
```

The seed tests check every rule below.

Components never import these files. ESLint blocks JSON imports in the apps, and the shared
package does not export the seed. All reads and writes go through `HiddenSpotDataService`.

## Business rules

These rules are implemented once in `packages/shared` and used by both apps.

**Places**

- Only `approved` places are visible.
- `averageRating` and `reviewCount` are always recomputed from the reviews, including reviews
  added on the device, so totals can never disagree with the list. A stored average is never
  trusted. Only valid ratings, whole numbers from 1 to 5, count. The average is the plain mean
  rounded to one decimal, or null with no valid reviews.
- Lists never contain two places with the same id. The first one wins, and seed validation
  rejects duplicate ids and slugs.

**Search**

- Fields searched: name, short and long description, category names, district and address.
  State, country and tags are not searched. Every place is in Kerala, so "kerala" would match
  everything.
- Case, accents and punctuation are ignored.
- Every query word must match the start of a word. "fall" finds "Falls", but "sea" does not
  find "season".
- Web and mobile wait 250 ms after the last keystroke before searching.

**Location and distance**

- Distances use the haversine formula with a mean Earth radius of 6,371 km.
- Coordinates are valid only when both are finite, latitude is from -90 to 90, and longitude is
  from -180 to 180. Missing or invalid coordinates mean "distance unknown", never 0 km.
- The reference location is either the device location, used only after the user allows it,
  or a demo town such as "Kochi (demo location)". The UI always says which one is used.
- A distance is shown only when both the place and the reference have valid coordinates.
- The radius filter applies only with a usable reference and a radius of 0 km or more. The
  boundary is inclusive. While it applies, places with unknown coordinates are hidden.
- Within one query, each distance is computed once and shared by the radius filter and the
  Nearest sort.

**Filters**

- Search, categories, districts, minimum rating, photos and radius all combine, so a place must
  pass every active filter. Changing one filter or the sort keeps the others.
- Category and district filters match any of the selected values.
- A minimum rating excludes places that have no reviews.

**Sorting**

| Sort         | Rule                                                                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Recommended  | Bayesian rating, or 3.8 when unrated, plus `0.25 × log10(popularity + 1)`. Synthetic places get -0.5. With a search, name matches first. |
| Nearest      | Ascending distance. Unknown coordinates last. Without a usable reference location it falls back to Recommended.                          |
| Most rated   | Bayesian rating, highest first. Ties go to more reviews. Unrated places last.                                                            |
| Newly added  | Latest `createdAt` first. Invalid dates last.                                                                                            |
| Most popular | Highest `popularityCount` first. Invalid counts count as 0.                                                                              |
| Name         | A to Z                                                                                                                                   |

The Bayesian rating is the single rating score used for ranking:

```text
score = (average × reviewCount + 3.8 × 3) / (reviewCount + 3)
```

The prior mean is 3.8 and the prior weight is 3, both set in `RATING_PRIOR`. One 5-star review
scores 4.1, while twenty reviews averaging 4.7 score 4.58. The score is rounded to six decimals,
so floating-point noise cannot break a genuine tie.

Every sort ends with a tie-break on name and then id. Text comparison does not use
`localeCompare`, because its results differ between Hermes on mobile and V8 on web. This keeps
the order identical on both platforms. The engine tests are in `packages/shared/tests/discovery.test.ts`.

**Reviews**

- Ratings are whole stars from 1 to 5. The body is 10 to 1000 characters and the title at most 80. The visit month uses YYYY-MM and cannot be in the future.
- One review per user per place.
- These rules live in `utils/reviewForm.ts`. The data service, the web review dialog and the
  mobile review sheet all use them, so they accept the same input and show the same messages.

**Submissions**

| From              | To                                      | Who       |
| ----------------- | --------------------------------------- | --------- |
| draft             | submitted                               | Submitter |
| submitted         | in_review, approved or rejected         | Moderator |
| in_review         | approved, changes_requested or rejected | Moderator |
| changes_requested | submitted                               | Submitter |

- `submitted` is shown as "Pending review". New submissions start there unless saved as a draft.
- Submission and review ids are generated, then checked against existing ids before use.
- `approved` and `rejected` are final.
- Moderator actions run as the fictional demo moderator. Nothing checks who is really using the
  app, so this is not security. A real backend must enforce moderator permissions on the server.
- `changes_requested` and `rejected` need a reviewer note of 5 to 500 characters. The admin page
  checks this with the same `validateModerationNote` rule as the service.
- Resubmitting clears the old note.
- A name that duplicates a listed place or open submission in the same district is rejected.
- Approving creates a public place. Unknown facts stay null and the rating starts at "New".

**Saved places**

- They are stored most recent first.
- Ids of places that no longer exist are ignored.
- Web and mobile keep separate lists, in localStorage and AsyncStorage. Nothing syncs between
  devices or apps.

Errors are thrown as `DemoDataError`. Each has a `code`, which is one of `VALIDATION`,
`NOT_FOUND`, `FORBIDDEN`, `INVALID_TRANSITION` or `CONFLICT`. Field-level `issues` can be shown
in forms.

## Service API

`HiddenSpotDataService` in `packages/shared/types/service.ts`. The Phase 1 implementation is
`DemoDataService`.

| Function                                          | Purpose                                    |
| ------------------------------------------------- | ------------------------------------------ |
| `getPlaces(query)`                                | Filter, sort and limit visible places      |
| `getPlaceById(idOrSlug)`                          | One place, or null                         |
| `searchPlaces(text, query)`                       | Text search with optional filters and sort |
| `filterPlaces(filters)`                           | Filters only, using the default sort       |
| `sortPlaces(places, sortBy, reference)`           | Pure and synchronous                       |
| `getCategories()`, `getDistricts()`               | Reference data                             |
| `getReviewsForPlace(placeId)`                     | Newest first, joined with authors          |
| `addDemoReview(input)`                            | Validated and stored on the device         |
| `getSubmissions(filter)`                          | Newest update first                        |
| `addDemoSubmission(input)`                        | Saves a draft or submits for review        |
| `updateDemoSubmissionStatus(id, update)`          | Enforces the lifecycle and roles           |
| `getSavedPlaces()`, `getSavedPlaceIds()`          | Saved list                                 |
| `toggleSavedPlace(placeId)`, `clearSavedPlaces()` | Change the saved list                      |
| `getDemoUsers()`, `getCurrentUser()`              | Demo accounts. The apps act as Anu Thomas. |
| `getStorageStatus()`, `resetDemoState()`          | Local storage health and reset             |
| `subscribe(listener)`, `getVersion()`             | Change notifications for screens           |

React apps use the hooks in `@hiddenspot/shared/react`: `usePlaces`, `usePlace`,
`useReviewsForPlace`, `useSubmissions`, `useSavedPlaces`, `useSavedPlaceIds`, `useCatalog`,
`useDistricts`, `useCurrentUser` and `useStorageStatus`. Hooks refetch automatically when demo
state changes.

## Persistence: local demo storage, not cloud sync

Seed data is read-only. Everything the user changes goes into a separate `DemoState`:

- reviews they added
- submissions they created
- status changes to seed submissions
- places created by approvals
- saved place ids

`DemoState` is stored as JSON under the key `hiddenspot:demo-state:v1`.

| Platform | Storage                                                      |
| -------- | ------------------------------------------------------------ |
| Web      | `localStorage`, per browser profile                          |
| Mobile   | `@react-native-async-storage/async-storage`, per app install |
| Tests    | In-memory storage                                            |

Nothing leaves the device. Clearing browser data or uninstalling the app removes it. Two devices
never share changes. The apps state this wherever saved data appears.

Failure handling:

- **Storage unavailable**, for example in private browsing or when blocked: changes are kept
  in memory for the session, and the apps show "Device storage is unavailable".
- **Corrupted JSON:** the raw value is copied to `hiddenspot:demo-state:corrupt-backup`, a clean
  state is saved, and the apps show "Some saved demo data could not be read and was reset".
- **Individual invalid entries:** only those entries are dropped. Valid data is kept.
- **A write fails later**, for example when the quota is full: the change is kept in memory and
  the status switches to memory-only.
- **Reset:** "Reset demo data" on the web Saved page and the mobile Profile screen returns to
  the seed data.

## Replacing demo data with an API later

1. Implement `HiddenSpotDataService` with `fetch` calls.
2. Run every response through `validatePlace`, `validateReview` and the other validators.
3. Return it from `createServices` in a new `'api'` mode.
4. Keep using the shared `queryPlaces` and `sortPlaces` for any client-side sorting, so behaviour
   stays identical.

Screens depend only on the interface and hooks, but the interface itself needs changes first,
such as removing client-supplied user ids. See [phase-2-backend-plan.md](phase-2-backend-plan.md).
